The application implements an Android Model-View-Controller (MVC) pattern:

- MODEL LAYER:
  * CassavaClassifier.kt: Handles model binary memory-mapping, input tensor 
    preprocessing (Bilinear 224x224 interpolation, Float32 conversion), TFLite

  * MainActivity.kt: Coordinates the application lifecycle, CameraX hardware 
    binding, asynchronous photo capture, gallery intent contracts, batch image 
    evaluation, confusion matrix metric computation, and local JSON persistence 
    in SharedPreferences.

  * activity_main.xml: Root navigation frame with CoordinatorLayout and BottomNavigationView.
  * layout_single_scan.xml: Single-leaf capture, live diagnosis cards, D-CLAHE visualizer view, 
    and past scan history.
  * layout_batch_test.xml: Multi-class batch evaluation interface with live image counters 
    and comparative metric dashboards.
  * HistoryAdapter.kt & BatchHistoryAdapter.kt: Bind records to RecyclerViews with 
    thread-isolated downsampling and individual item deletion.

7. COMPREHENSIVE Q&A CHEATSHEET FOR THE DEFENSE PANEL
================================================================================

Q1: What is the core hypothesis of your thesis?
A: Our research examines whether applying D-CLAHE (Dual / Directional Contrast Limited 
   Adaptive Histogram Equalization) preprocessing improves deep learning classification 
   accuracy and feature saliency on cassava leaf diseases compared to standard unenhanced imagery.

Q2: Why does the mobile app feature both a Base Model and an Enhanced Model?
A: To provide empirical, live proof of the enhancement effect in real-time. By feeding the 
   exact same input photo to both models simultaneously, the panel and users can directly 
   observe the difference in confidence, class probabilities, and diagnostic accuracy.

Q3: What exact preprocessing steps occur before feeding an image to TensorFlow Lite?
A: 1. Bitmap Decoding: Decodes camera capture or gallery image to an ARGB_8888 Bitmap.
   2. TensorImage Wrapper: Wraps the bitmap in TensorImage(DataType.FLOAT32).
   3. Spatial Rescaling: Uses ImageProcessor with ResizeOp(224, 224, BILINEAR) to scale 
      the image to the expected 224x224 input resolution.
   4. Tensor Buffer Alignment: Memory-maps the resulting float buffer into shape [1, 224, 224, 3].

Q4: Why did you include Matthews Correlation Coefficient (MCC) in the batch metrics?
A: Agricultural field datasets are inherently class-imbalanced (e.g., CMD is far more prevalent 
   than CBB). Standard Accuracy is misleading on imbalanced datasets because a model predicting 
   only the majority class can still achieve high accuracy. MCC takes into account all four 
   confusion matrix quadrants (TP, TN, FP, FN) and produces a score between -1 and +1, where a 
   high score is achieved only if predictions are balanced across all classes.

Q5: How does the application prevent OutOfMemory (OOM) errors and UI stuttering?
A: 1. Models are loaded via MappedByteBuffer using FileChannel.map(), which maps the model 
      directly into virtual memory without consuming Java heap space.
   2. In HistoryAdapter, high-resolution leaf images are decoded on a background thread pool 
      (Executors.newFixedThreadPool(4)) using BitmapFactory.Options.inSampleSize to downsample 
      them to ~100x100 thumbnails before allocating memory.
   3. ImageView tagging (holder.imgHistory.tag = imgPath) prevents incorrect bitmap recycling 
      during rapid scrolling.

Q6: How does data persistence work?
A: To maintain lightweight efficiency without the overhead of an SQL/Room database, history 
   records are serialized into JSON arrays using Android's native org.json package and saved 
   into private Android SharedPreferences. Captured images are stored in the application's 
   internal cache directory (cacheDir).
